# PVLT0003 storage design

## First implementation status

The current implementation creates PVLT0003 collections with an append-only stream of encrypted item blocks and authenticated, versioned index deltas with a full checkpoint every 32 commits. Existing PVLT0003 full-index snapshots remain readable. New commits have a redundant footer seal with a checksum, so a damaged footer signature is reported as a corrupt commit rather than an incomplete tail; an unsealed tail is treated as an interrupted append. Legacy commits remain readable. Index opening authenticates the encrypted index and commit chain without rereading all payload bytes; legacy transaction digests are not rescanned because every live encrypted block is authenticated when read, and `Service.Verify` scans every live item and checks its SHA-256. Deletes are represented as delta operations; checkpoints materialize the live view. New headers wrap a random DEK in two crash-tolerant password slots; `Service.ChangePassword` rotates the envelope without rewriting payload blocks. `Service.RotateDataKey` creates a new DEK and re-encrypts all live items. PVLT0002 and early direct-key PVLT0003 migrations, and compaction, authenticate each copied item before replacing the source. The UI exposes password change, DEK rotation, verification, and compaction in its Security tab.

The implementation still uses encrypted JSON index payloads and legacy item-record framing. It does not yet include a tail locator, object IDs, frame-level record types, or platform crash-injection coverage. Those remain format hardening tasks before treating PVLT0003 as a long-term stable interchange format.

## Goals

PVLT0003 should make metadata edits and single-file changes proportional to the changed data, preserve a readable committed state after an interrupted write, and keep PVLT0001/PVLT0002 readable. The format must support explicit compaction and password changes without re-encrypting every file payload.

## Key hierarchy

- Generate a random 256-bit data-encryption key (DEK) when creating a PVLT0003 collection.
- Derive a key-encryption key (KEK) from the password and a per-collection salt using the recorded KDF identifier and parameters.
- Store an authenticated DEK envelope in the immutable header. Changing the password writes a new envelope under the new KEK; file records remain encrypted under the DEK.
- Record type, format version, collection ID, object ID, object version, chunk number, and declared plaintext length are authenticated as AEAD associated data.
- Each encrypted record gets a fresh CSPRNG nonce. Readers reject unknown algorithms, invalid KDF parameters, oversized lengths, and unsupported record versions before allocating payload buffers.

The first implementation should retain AES-256-GCM and explicitly version the KDF and AEAD identifiers. Algorithm agility is a format field, not a reason to accept unknown algorithms.

## Append log and index

The immutable header is followed by framed records. Every frame has a fixed magic, frame version, record type, bounded payload length, transaction ID, encrypted payload, and authentication tag. Initial record types:

- `DATA`: encrypted file content, chunked at 1 MiB, with a stable object ID and content hash.
- `PUT`: add or replace a path and point it at a data record; include size, hash, object ID, and tag IDs.
- `TOMBSTONE`: remove a path or object ID from the live view.
- `TAG`: create, edit, or delete a tag definition and update tag assignments.
- `CHECKPOINT`: a versioned encrypted index snapshot that records the live path map and tag catalog.
- `COMMIT`: transaction sequence, previous committed-record hash, the new index root/checkpoint reference, and a digest of all frames in this transaction.

The live index is a versioned map. Transactions append deltas and a commit record. Checkpoints bound replay time; the initial policy should checkpoint after a configurable number of deltas or when replay bytes exceed a configured limit. Metadata edits append small deltas and do not copy file payloads. Deletes append tombstones; old encrypted data becomes reclaimable during compaction.

## Commit and crash recovery

All mutating operations hold the existing cross-process collection lock and follow this order:

1. Find and authenticate the last committed transaction; ignore bytes after it.
2. Append data and index-delta frames for one transaction.
3. Sync the appended frames.
4. Append the authenticated `COMMIT` frame, linking it to the prior commit and the transaction digest.
5. Sync the commit frame before reporting success or clearing imported source files.

Opening validates frame bounds, AEAD tags, sequence numbers, previous-commit linkage, and transaction digests. Only records reachable from the last valid commit are visible. An incomplete tail is ignored on read. Before the next write, recovery truncates only the uncommitted tail under the write lock, then appends a new transaction. A complete but invalid commit is corruption and must be reported; it must not silently expose an older view as if no corruption occurred.

The scanner should use bounded buffers and seekable checkpoints. A normal open should find the latest commit from a fixed-size tail locator; if that locator is torn, a backward scan searches for the latest authenticated commit marker and follows its previous-commit links. The locator is a hint only; it is not trusted without authentication.

## Compaction

Compaction writes a fresh temporary PVLT0003 file containing the current live data records, a checkpoint, and a new commit chain root. It verifies every copied record and the resulting index, syncs the file, closes all old-container descriptors, and atomically replaces the collection. It omits tombstoned and unreachable records. Existing readers retain their old snapshot through their open file handles. The operation must preserve the DEK envelope so payloads can be copied without decrypting and re-encrypting them.

Compaction is explicit at first. Automatic triggers can be added after measuring live-to-dead byte ratio and rewrite cost. Failed compaction leaves the old collection intact and removes the temporary file on normal error paths; startup cleanup handles abandoned temporary files.

## Migration and compatibility

PVLT0003 is opt-in until the reader, writer, recovery, and compaction paths pass the stability suite. PVLT0001 and PVLT0002 remain read-only supported formats. Migration reads the old collection, writes and verifies a sibling PVLT0003 candidate, syncs it, then atomically installs it while retaining the original as a backup. A failed migration never replaces or deletes the source. The application reports the source and target versions before starting a potentially long migration.

## Failure-injection and acceptance tests

- Round-trip files, tags, replacements, tombstones, and duplicate handling.
- Crash after each append/sync step; reopen must expose either the previous commit or the complete new commit, never a partial transaction.
- Corrupt or truncate each frame field, ciphertext, index root, commit digest, and tail locator.
- Two-process writers must serialize without losing committed changes.
- Existing sessions must read their original snapshot during append, compaction, and atomic replacement on macOS and Windows.
- Compaction must preserve hashes and tags while removing dead bytes; interrupted compaction must preserve the original file.
- Password change must preserve all payload hashes while invalidating the old password and accepting the new one.
- DEK rotation must re-encrypt all live payloads with a new random key while preserving their contents and password.
- Fast open must avoid reading all item payloads; full verification must detect corrupted records and hashes.
- Fuzz frame and decrypted-index parsers separately; benchmark open/replay, append, compaction, and process RSS on representative 1/10/100 GiB collections.

## Implementation sequence

1. Write a standalone PVLT0003 parser and format document tests without changing PVLT0002 behavior.
2. Add frame encoding, encryption, and authenticated commit-chain recovery.
3. Add versioned index deltas and checkpoints, then route create/add/delete/tag operations through the new writer. (Implemented; checkpoints are written every 32 commits.)
4. Add atomic migration and explicit compaction. (Implemented for PVLT0002 and direct-key PVLT0003.)
5. Add UI progress/cancellation for long operations.
6. Enable PVLT0003 as a stable interchange format after cross-platform crash-injection and performance acceptance tests pass.
